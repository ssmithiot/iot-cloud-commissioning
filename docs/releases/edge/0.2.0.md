# Edge Release 0.2.0

Status: Release candidate RC2. Local validation complete; GW006 pilot not yet
run. RC2 corrects the Trend Viewer; see "Trend Viewer correction (RC2)".

Base release: Edge 0.1.9

## Scope

Edge Trends work. 0.1.9 shipped local trend collection disabled as an approved
temporary exception, recorded in `docs/authoritative/PROJECT_STATE.md` §2, while
a non-interfering BACnet implementation was completed. 0.2.0 completes it and
turns collection on.

- Edge UI: `EDGE_TRENDS_UI_ENABLED` defaults to `1`. Trend Groups and Trend
  Viewer are reachable. Numeric, binary and multistate parsing and the supported
  time ranges are unchanged from the preserved implementation; the viewer itself
  was corrected in RC2, described under "Trend Viewer correction (RC2)" below.
- Edge agent: `local_edge_trends_enabled` defaults to `true`, plus the
  performance isolation described below and a working upload path for
  Edge-collected samples.
- Cloud API: a mirror for Edge-owned samples. Migration `0022` created
  `edge_local_trend_samples` in the 0.1.9 line but no model or route ever used
  it; 0.2.0 supplies both.
- No change to `bacrp`, `bacrpm` or `bacwp`.

## Trend Viewer correction (RC2)

RC1 shipped a viewer that misrepresented long time ranges. Five defects were
found and corrected before the GW006 pilot. This is a UI and query change only:
BACnet sampling, locks, ports, router behaviour, collection intervals, cloud
ownership and upload behaviour are untouched, and no stored sample is deleted,
shortened or rewritten.

| Defect in RC1 | Correction in RC2 |
|---|---|
| Trend Groups offered "View samples", which opened the viewer in table mode | The action is "View" and opens the graph, which is now the only viewer mode |
| Separate Table view and Graph view controls, though the graph page already carried a sample table | The standalone table mode and its navigation are gone; the sample table stays below the graph |
| Saved view settings reset on every range change, because range links, the custom-hours form and the save redirect all dropped the view ID | Every range link and form carries the selected view ID, and the save captures the ID returned by `store.save_view()` and redirects with it, preserving range and custom hours |
| The viewer asked for 50,000 rows while `EdgeTrendStore.samples()` clamped every query to the newest 2,000, so 2-day and 7-day ranges showed only their tail | Graph data is separate from table data (below). Both range controls are retained |
| A permanent right-side points-and-axes panel consumed chart width | The panel is an expandable control above the chart; the chart uses the full content width |

### Graph data versus table data

`EdgeTrendStore.samples()` answers "the newest N rows". That is right for the
table and wrong for the graph: one fast-sampling point could consume the whole
budget, hide every other point in the group, and leave a 7-day request drawing a
few hours.

`EdgeTrendStore.graph_samples()` is the graph's own query path. It walks each
trend point independently and gives each one its own budget, so no point can
crowd another out. A point whose window holds more rows than the target is
reduced by time bucket, keeping the first, minimum, maximum and last sample of
every bucket, so the plotted line spans the full period and short spikes and
excursions remain visible. Rows are returned in chronological order. Reduction
happens in the query path while streaming the cursor, so memory is proportional
to the bucket count rather than to the raw row count.

| Path | Bound | Purpose |
|---|---|---|
| Graph | ~2,000 plotted values **per trend point**, whole requested window | `graph_samples()` |
| Recent samples table | Newest 500 raw rows for the group and range | `samples()` |

Both bounds are display limits. Every raw sample remains in SQLite; a 7-day view
now visibly spans seven days whenever seven days of data exist.

## Trend ownership

The Edge owns saved devices, saved points, trend groups, group names, included
points, enabled state, sampling intervals, local history and collection status.

The cloud mirrors samples for display. There is no cloud route that creates,
edits or deletes an Edge trend group, and this is asserted by
`cloud-api/tests/test_edge_local_trend_mirror.py`.

## Rule #1 — trend collection must not degrade live BACnet work

The performance baseline is unchanged: BACnet/IP live reads under 1 second,
MS/TP live reads approximately 3 seconds. 0.2.0 protects it as follows.

| Mechanism | Setting | Default |
|---|---|---|
| Trend reads give up the runtime lock quickly instead of queueing behind live work | `trend_lock_timeout_sec` | 2 s |
| Operator reads and writes keep the full lock wait | `bacnet.lock_timeout_sec` | 30 s |
| Trend reads are split into bounded batches, lock released between them | `trend_read_batch_size` | 8 points |
| One cycle cannot monopolise the runtime | `trend_max_points_per_cycle` | 200 points |
| Upload batch is bounded | `trend_local_upload_batch_size` | 200 samples |

Behaviour:

- A group does not start while the BACnet runtime lock is held. No run row is
  written, so a busy moment costs one retry rather than a whole interval.
- Between batches, the agent re-checks for live work and yields the runtime.
  Unread points are recorded as `deferred`, never as samples.
- `deferred_count` now means "points not read because BACnet was busy". A
  missing or failed read remains a stored sample carrying its quality status.
  A failure is never recorded as a good value.
- No global throttle, serialisation wrapper, shared queue, broad lock,
  artificial delay or new retry behaviour was added to the proven read/write
  paths. No new BACnet port. No change to router profiles or to GW006's port
  arrangement.

## Data protection

- The Edge UI trend store upgrades an existing database additively: missing
  tables are created, missing columns are added, and nothing is dropped,
  rewritten or migrated away.
- A backup is written next to the database (`edge-trends.db.pre-<version>-<UTC
  timestamp>.bak`) before the first statement that would change a populated
  database. Reruns are no-ops and take no further backup.
- Cloud migration `0022` is additive and guarded by `has_table`, so it is safe
  to rerun.
- Trend groups, points, runs, samples, outbox entries, saved devices, gateway
  configuration, credentials and BACnet port configuration are preserved.
  Disabling a group retains its history. A group is deleted only by an explicit
  user delete action.

## Cloud outage behaviour

Sampling reads configuration from the gateway's own trend database on every
cycle and does not consult the cloud. Collection continues during an outage;
samples accumulate in the Edge outbox and are uploaded when connectivity
returns. Upload is idempotent on the gateway-generated `event_id`, so a retry
after a lost acknowledgement cannot create a second copy of a reading. The
backlog survives an agent restart.

## Branch provenance

`release/edge-agent-0.2.0` was branched from `release/edge-agent-0.1.9`
(`e634e77`), not from `main`. `main` still declares agent `0.1.6` and contains
none of the 0.1.8/0.1.9 release work.

The agent payload at the branch point is byte-identical to the authoritative
0.1.9 baseline `d2722d395ab3b380f8858b5208863a8e49ff2cc3`: both resolve
`edge-agent/` to tree `fdea438fcf435bce6b4128697d3401a295c0b7da`. The branch
therefore inherits the deployed agent exactly, plus the cloud-side release
tooling and migrations `0022`/`0023` that the `edge-agent-v0.1.9-final` tag
already names as part of the release.

`release/edge-ui-0.2.0` was branched from `release/edge-ui-0.1.9`
(`719d4a82ed972269d44db7c0638800b26e82002d`, tag `edge-ui-v0.1.9-final`). The
Edge UI `main` branch is an unrelated history with no common ancestor and was
not used.

Inheriting the maintenance line means 0.2.0 carries the 16 post-baseline
commits recorded as OPEN-03 in `docs/authoritative/KNOWN_ISSUES.md`, whose
cloud-side approval was undecided. This is a deliberate choice, not a silent
one, and it does not redefine release 0.1.9.

## Compatibility with gateways on 0.1.9

- Agent-to-cloud: additive only. 0.2.0 adds
  `POST /api/edge/{gateway_id}/local-trend-samples`. No existing endpoint,
  request or response changed, so a 0.1.9 agent keeps working against a cloud
  running 0.2.0.
- Cloud-to-agent: unchanged. A 0.2.0 agent against an older cloud logs a failed
  upload and retries with backoff; local collection is unaffected.
- Database: migration `0022` is additive and already present in the 0.1.9
  maintenance line. Alembic head is unchanged at `0023_edge_release_targets`.
- Trend gates: a gateway upgraded to 0.2.0 gets trends on by default. A gateway
  left on 0.1.9 keeps them off. Mixed fleets are supported; the two gates are
  independent per gateway.
- Rollback target is 0.1.9, which is reproducible from
  `tools/releases/gw006-edge-ui-0.1.9-code.tar.gz` and agent commit `d2722d3`.
  This is a stronger rollback position than 0.1.9 had, whose declared 0.1.8
  target is unrecovered (OPEN-01).

## Configuration

Both gates must be set. They live in different components.

```
# Edge UI service environment
EDGE_TRENDS_UI_ENABLED=1

# /etc/iot-cx-agent/agent.yaml
local_edge_trends_enabled: true
edge_ui_data_dir: /home/swadmin/edge-bacnet-ui-v2/data
```

Setting only one produces a trend interface with no samples, or samples with no
interface. The Edge UI's disabled page states this.

## Upgrade

1. Take the pre-update code checkpoint: `/home/swadmin/gw-recovery/0.2.0/`.
2. Deploy the embedded validated artifact through the Legacy Updater. The
   updater refuses to proceed unless the manifest checksum and artifact
   contents validate.
3. Update `/etc/iot-cx-agent/agent.yaml` if `edge_ui_data_dir` is not already
   set; `local_edge_trends_enabled` defaults to true and need not be added.
4. Restart `edge-bacnet-ui.service`, then `iot-cx-agent.service`.
5. Confirm the UI footer reads `Edge Release 0.2.0` and that Trend Groups is
   reachable.

The first agent cycle after restart creates the trend database backup if the
schema needs changes. `data/`, `.env`, `start.sh`, credentials, gateway
identity, saved devices, templates, programs, trends, timed overrides and
BACnet route settings are preserved.

## Validation and rollback

Local test results are recorded in `docs/releases/edge/validation/0.2.0.md`.
GW006 pilot validation is **not complete**; the same document states what
remains before this candidate may be deployed.

Rollback is the existing Legacy Updater code-only checkpoint restore from
`/home/swadmin/gw-recovery/0.2.0/pre-update-code.tar.gz`, which restores the
0.1.9 UI code without touching gateway state.

To stop trend collection without a code rollback, set
`EDGE_TRENDS_UI_ENABLED=0` and `local_edge_trends_enabled: false` and restart
both services. Existing groups and history are retained.

If the trend database itself must be reverted, the pre-upgrade copy is beside
it as `edge-trends.db.pre-2-<UTC timestamp>.bak`.
